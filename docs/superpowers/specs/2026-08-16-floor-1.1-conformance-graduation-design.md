# Floor 1.1 Conformance Graduation Design

## Purpose

Graduate the three fixture families that Floor 1.1 currently reports as `unsupported` into executable conformance proofs without expanding Project0's ontology or introducing a second fixture architecture.

Target families:

- `sealed-plurality-round-trip` — P0-I3, P0-I5
- `repair-scar-round-trip` — P0-I5, P0-I14
- `monument-build-beside` — P0-I1, P0-I3

This is the bounded implementation slice tracked by #35. It advances #3/#10 but does not close either broader issue.

## Governing constraints

- Reuse `CanonicalNode`, `CanonicalRelationship`, `CanonicalReceipt`, `ReceiptGraph`, and the existing canonical-addressing path.
- Do not add node kinds, relationship kinds, receipt kinds, or a fixture DSL.
- Do not change canonical Node/Edge/Receipt/Request addressing.
- Keep the conformance CLI deterministic, offline, model-independent, and network-independent.
- Each newly passing fixture must cite canonical addresses produced by the existing address functions.
- A fixture passes only when the meaning-bearing distinction it claims to test is mechanically visible.

## Chosen architecture

Keep the three specimens as focused functions in `src/reference-kernel/conformance.ts`, alongside the existing Floor 1.1 conformance functions. Use canonical relationships when a typed relation is the evidence being tested and use `ReceiptGraph` when append-only history is the law being tested.

A generic fixture engine is intentionally deferred. The current need is three concrete executable truths, not a second abstraction layer.

## Specimen 1 — sealed plurality

Construct two independent `observation` nodes with the same apparent subject but distinct attribution/body claims. Address both independently. Construct one `harvest` node whose provenance cites both parent addresses. Address two `compresses` relationships from the harvest to the two parents.

The specimen passes only when:

1. the two parent node addresses are distinct;
2. re-addressing each parent after synthesis yields its original address;
3. the harvest has its own distinct address and retains both parent refs in provenance;
4. both `compresses` edges are independently addressable and target the correct parent;
5. neither parent disappears or is rewritten by the later synthesis.

Evidence refs include both parents, the harvest, and both relationship addresses.

## Specimen 2 — repair scar

Append an original `WitnessReceipt` to a fresh `ReceiptGraph`. Record its canonical address and recovered bytes/structure. Append a later `DispositionReceipt` with `previousReceiptRefs` containing the original receipt ref and outputs that explicitly identify a repair/dispute disposition.

The specimen passes only when:

1. the original receipt appends successfully;
2. the repair receipt appends successfully as a child of the original;
3. `childrenOf(originalRef)` returns the repair receipt;
4. re-addressing/re-reading the original after repair yields the original identity and structure;
5. the repair has a distinct canonical receipt address.

Evidence refs include the original and repair receipt addresses.

## Specimen 3 — monument / build beside

Construct a `source` node whose body explicitly declares its local fixture status as `monument`/closed. Address it. Construct a new `proposal` node as an attributable neighboring branch whose provenance cites the monument. Address a `continues` relationship from the proposal to the monument.

The specimen passes only when:

1. re-addressing the monument after branch construction yields the original address;
2. the branch has a distinct canonical identity;
3. the branch provenance contains the monument address;
4. the `continues` relationship explicitly connects branch to monument;
5. the branch does not reuse the monument address or claim to replace its bytes.

The `monument` marker remains fixture-local body data. It does not become a new universal node kind or kernel state machine.

Evidence refs include monument, branch, and relationship addresses.

## Error handling

Each specimen is fail-closed. Unexpected exceptions become `fail` results with stable surfaced error text, matching the existing conformance style. Mechanical mismatch returns a fixture-specific reason code string rather than silently passing.

No new normative reason-code constants are required because these are conformance-result diagnostics, not new kernel admission/refusal semantics.

## Testing strategy

Use repository-level RED → GREEN TDD through GitHub Actions because the current execution host cannot resolve GitHub from the local shell.

RED:

- change the conformance tests to require all three families to report `pass`, cite evidence, and render as `PASS`;
- open a draft PR with no production implementation change;
- observe `npm run verify:all` fail specifically because the existing implementation still returns `unsupported`.

GREEN:

- implement the three bounded specimen functions;
- rerun the exact PR workflow;
- require all TypeScript, Node tests, Python fixture verification, and conformance CLI checks to pass.

## Compatibility and migration

Additive conformance coverage only. Canonical identity grammar, frozen ontology, existing receipt semantics, and existing supported fixture behavior remain unchanged. The only report-level behavior change is that three known fixture rows move from `UNSUPPORTED` to executable `PASS` when the reference kernel satisfies them.
