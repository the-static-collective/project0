# L-Branch v0.1 — Bounded Resonant Propagation Design

## Status

Approved design direction for Project 0 issue #46. This document specifies the smallest Project 0-owned contract boundary for bounded resonant propagation. It does not implement an autonomous agent runtime and does not alter the frozen nine-kind ontology.

## Design sentence

> One admitted excitation may propagate through a predeclared local topology for a finite amount of work; propagation may expand search, but it may never expand sovereignty.

Human-facing compression:

> Beetle stores the shape. Bumblebee makes the shape ring.

The biological image is design lineage only. Project 0 does not depend on any biological claim beyond the useful systems pattern: sparse excitation can produce repeated local response when structure participates in the cycle.

## Purpose

Project 0 already has adjacent pieces that should not be duplicated:

- Resonance Seeds (#27) describe sparse attractor inputs without requiring one predetermined realization.
- Resonant Tension (#30, extracted from historical PR #17) describes pure evaluation that may discover a useful relationship while preserving dissent and refusing to manufacture authority.
- NAV v0.1 describes bounded before/crossing/after difference.
- World Encounter Envelope v0.1 carries attributable testimony across a declared boundary while destination authority stays local.
- the reference kernel already supplies canonical addressing, append-only receipt history, explicit authority consumption, and deterministic verification.

What is missing is a law for **bounded propagation after admission**.

The target is not “agents may keep acting.” The target is narrower:

```text
admitted excitation
      ↓
fixed local eligibility law
      ↓
step receipt
      ↓
new local evidence
      ↓
next eligibility evaluation
      ↓
...
      ↓
explicit terminal receipt
```

A branch should be able to ring without requiring a new external command for every micro-step, while remaining finite, replayable, least-privileged, and incapable of enlarging its own authority.

## Classification and boundary

This is an architectural addition above ontology v0.1 because it defines a new portable process contract that downstream products may implement. The first executable slice must nevertheless remain **fixture-sized**.

Project 0 owns:

- versioned declaration semantics;
- deterministic eligibility and termination semantics;
- canonical step and terminal receipt semantics;
- authority/disclosure conservation requirements;
- adversarial conformance fixtures.

Project 0 does not own:

- orchestration UX;
- model selection;
- agent prompts;
- queues or schedulers;
- databases;
- remote execution;
- product-specific candidate generation;
- creative scoring;
- autonomous runtime policy.

Those remain downstream or deferred.

## Naming boundaries

Existing terms must retain their meaning.

### BEE Protocol

BEE remains **Boundary-Carried Invariants**. L-Branch does not rename, replace, or overload it.

### Pollen Scout

Pollen Scout remains Founder Node’s evidence-backed nearby-growth projection. It identifies relevant doors; it does not become a generic transport or execution protocol.

### Bumblebee

“Bumblebee” is the informal biological analogy for L-Branch. It is not a protocol acronym and should not appear as a canonical machine identifier.

### Pollen

“Pollen” may remain a human-facing metaphor for influence-without-authority. The first Project 0 slice should not mint a second exchange envelope merely to support the metaphor. Influence inputs should be ordinary content-addressed refs whose epistemic/authority status remains explicit.

## Considered approaches

### A. Autonomous agent loop

A controller accepts an objective and repeatedly dispatches work until it decides it is done.

Rejected for this slice. It violates the current Project 0 roadmap boundary, introduces model/runtime behavior before a deterministic contract exists, and makes authority conservation harder to prove.

### B. Generic recursive workflow engine

Define a universal state-machine/orchestration format capable of arbitrary branching, retries, tool calls, and scheduling.

Rejected. It is substantially larger than the missing law and would make Project 0 own infrastructure rather than semantics.

### C. Deterministic bounded propagation contract

Declare the local topology, available authority, policy context, evaluator version, continuation law, and finite budget before execution. Evaluate fixture-local candidate transitions with pure functions. Emit append-only step and terminal receipts.

Selected. This is the smallest design that proves “structure can participate in motion” without importing autonomous runtime semantics.

## Core model

An L-Branch has five conceptual layers.

### 1. Declaration

The complete execution envelope is declared before propagation starts.

A declaration must identify:

- protocol/version;
- canonical starting snapshot;
- admitted excitation;
- declared purpose;
- participant/topology refs available to the branch;
- policy/disclosure context;
- evaluator identity/version;
- authority refs available to the branch;
- finite propagation budget;
- deterministic continuation and terminal rules.

The declaration is content-addressed using the repository’s existing canonical addressing law.

### 2. Eligibility

Each step evaluates only declared candidates against fixed rules and current branch-local receipt history.

Eligibility may depend on:

- explicit candidate refs;
- explicit prior recognition/tension/evidence refs;
- declared policy/disclosure;
- declared authority;
- previous step receipts;
- remaining budget;
- deterministic fixture-local rules.

Eligibility must not depend on:

- hidden global state;
- model confidence as evidence;
- undeclared search;
- ambient repository visibility;
- branch success manufacturing new capability;
- prior influence refs becoming authority.

### 3. Propagation

A successful step may make a later declared candidate eligible. That is the entire self-propagating seam.

No step receives new sovereignty simply because a prior step succeeded.

The admissible authority set is fixed at branch admission:

```text
authority_used(step_n) ⊆ authority_declared(branch)
```

Across the whole branch:

```text
union(authority_used(all_steps)) ⊆ authority_declared(branch)
```

Authority may be consumed or exhausted according to existing lease rules. It may never be minted by resonance, recurrence, evidence, similarity, or successful propagation.

### 4. Damping

L-Branch requires explicit finite termination. A branch is not permitted to “continue until satisfied.”

The minimum budget is:

```ts
type PropagationBudget = {
  maxSteps: number;
  maxFrontierWidth: number;
  maxDepth: number;
};
```

The first implementation may choose a simpler internal representation if it preserves the same three limits.

A branch damps when no further declared candidate satisfies the continuation law before budget exhaustion.

### 5. Terminal history

Every branch ends with one explicit terminal disposition:

```ts
type LBranchTerminalDisposition =
  | "completed"
  | "damped"
  | "refused"
  | "exhausted"
  | "inadmissible";
```

No branch disappears silently.

## Proposed experimental contracts

Exact field names remain implementation-level choices, but the first slice should preserve this semantic shape.

```ts
type LBranchDeclaration = {
  protocol: "p0.l-branch/0.1";
  snapshotRef: ContentAddress;
  excitationRef: ContentAddress;
  purposeRef: ContentAddress;
  participantRefs: ContentAddress[];
  influenceRefs: ContentAddress[];
  authorityRefs: ContentAddress[];
  evaluatorId: string;
  evaluatorVersion: string;
  policyRef: ContentAddress;
  budget: PropagationBudget;
};
```

`influenceRefs` are deliberately not authority refs. The implementation must keep the arrays semantically and mechanically distinct.

A step receipt should minimally recover:

```ts
type LBranchStepReceipt = {
  branchRef: ContentAddress;
  stepIndex: number;
  depth: number;
  inputRefs: ContentAddress[];
  consideredRefs: ContentAddress[];
  eligibleOutputRefs: ContentAddress[];
  refusedOutputRefs: ContentAddress[];
  authorityRefsUsed: ContentAddress[];
  influenceRefsConsulted: ContentAddress[];
  remainingBudget: PropagationBudget;
};
```

The terminal receipt should minimally recover:

```ts
type LBranchTerminalReceipt = {
  branchRef: ContentAddress;
  disposition: LBranchTerminalDisposition;
  stepReceiptRefs: ContentAddress[];
  finalOutputRefs: ContentAddress[];
  refusedAttemptRefs: ContentAddress[];
  authorityRefsUsed: ContentAddress[];
  unusedAuthorityRefs: ContentAddress[];
  remainingBudget: PropagationBudget;
};
```

These should be expressed through the existing receipt/canonicalization machinery rather than creating a second graph, chain, hasher, or timestamp-derived identity scheme.

## Pollen / influence law

The useful software translation of pollen is:

> Encounter can alter future susceptibility without acquiring execution authority.

Mechanically, an influence ref may alter an eligibility result while the branch authority set remains identical.

Example fixture:

```text
without recognition R:
  candidate C = ineligible

authority refs = [lease-A]

with recognition R:
  candidate C = eligible

authority refs = [lease-A]
```

The observable change is candidate susceptibility, not sovereignty.

This is the critical conformance distinction. If adding an influence ref also enlarges authority, the implementation fails.

## Load law

Problem difficulty may alter the declared search budget before branch admission.

For example:

```text
low load
maxSteps: 3
maxFrontierWidth: 2
maxDepth: 2

high load
maxSteps: 9
maxFrontierWidth: 4
maxDepth: 3
```

The authority and disclosure envelope must remain independently declared. Increasing work budget cannot alter:

- authority refs;
- capabilities;
- source scopes;
- disclosure permissions;
- participant identities.

This is the computational form of:

> Difficulty expands search, not sovereignty.

## Refusal topology

An attempted candidate that fails eligibility is not equivalent to a candidate that was never considered.

The first fixture should preserve at least:

- candidate ref;
- branch/step ref;
- deterministic refusal reason code;
- evidence/policy/authority basis consulted;
- whether the refusal resulted from scope, disclosure, authority, topology, or budget.

The refusal must remain historical evidence without automatically becoming future policy.

Later branches may explicitly consult the refusal as an influence ref. That consultation may alter search ordering or eligibility under a declared rule, but the old refusal cannot silently become an authority grant or permanent prohibition.

## Relationship to Resonance Seeds (#27)

A Resonance Seed can supply the sparse structure that shapes a branch field. L-Branch does not require a seed, but when one is present:

```text
Seed
  ↓ shapes susceptibility
Declared L-Branch
  ↓ bounded propagation
Realization / terminal output
  ↓
Recognition
  ↓ may influence a later branch
```

The seed, branch, realization, and recognition remain separately addressed. Recognition cannot rewrite prior branch history.

## Relationship to Resonant Tension (#30)

The #30 evaluator answers whether a declared tension admits a useful resonance candidate, productive dissonance, no resonance, or inadmissibility.

L-Branch may invoke that deterministic evaluator as one eligibility step once #30 has an executable version boundary. It must not absorb or redefine #30.

A productive-dissonance result is a lawful branch result. L-Branch is not required to converge.

## Relationship to World Encounter

World Encounter carries attributable testimony into another declared boundary while destination authority remains local.

An encounter envelope may later appear as an L-Branch influence ref. The envelope’s successful transport does not transfer source authority into the branch.

The receiving branch evaluates the ref under its own policy, disclosure, purpose, and authority declaration.

## Failure behavior

The contract fails closed.

### Inadmissible declaration

Return `inadmissible` when:

- starting snapshot identity cannot be verified;
- protocol/version is unsupported;
- evaluator identity/version is absent;
- purpose is absent;
- declared topology is malformed;
- budget is missing, zero/negative, or exceeds implementation policy;
- policy/disclosure context is unverifiable.

No step execution occurs.

### Refused step

Record a refused attempt when a declared candidate exists but cannot lawfully execute because:

- required authority is absent/exhausted;
- disclosure does not permit the candidate material;
- scope crossing lacks valid basis;
- candidate lies outside declared topology;
- continuation law rejects it.

A refused candidate cannot be silently dropped from history.

### Exhausted branch

Return `exhausted` when a further step would otherwise be eligible but the declared budget no longer permits it.

### Damped branch

Return `damped` when budget remains but no declared candidate satisfies continuation.

### Completed branch

Return `completed` only when a separately declared terminal condition is met. “The evaluator feels finished” is not a terminal rule.

## Observability

Each branch needs one stable trace identity: its content-addressed declaration ref.

Every step receipt must reference that branch ref and its predecessor history strongly enough to reconstruct exact ordering.

No private chain-of-thought or model scratchpad belongs in the receipt. The receipt preserves explicit inputs, outputs, rule/evaluator identity, refusal reasons, budget, and authority use.

This is sufficient to answer:

- what entered the branch;
- what was considered;
- what became eligible;
- what was refused;
- which authority was consumed;
- what influence was consulted;
- why propagation stopped.

## Security / least-privilege rules

1. Candidate enumeration happens **after** disclosure/permission checks for material that is not already safely declared.
2. No stable identifiers for inaccessible external material leak into branch receipts.
3. `influenceRefs` and `authorityRefs` are distinct typed fields.
4. A branch cannot add a participant ref after admission in v0.1.
5. A branch cannot add an authority ref after admission in v0.1.
6. Budget changes require a new branch declaration/address in v0.1.
7. Every evaluator version change changes branch identity or evaluation identity as appropriate; replay never silently crosses evaluator versions.

## TDD / executable specimen strategy

The first implementation should follow a strict RED → GREEN sequence and remain offline.

### RED 1 — contract absent

Add a test importing the not-yet-existing experimental L-Branch module and specifying one three-candidate fixture:

```text
excitation E
  ↓
A eligible
  ↓
B eligible because A receipt exists
  ↓
C refused because required authority is absent
  ↓
damped
```

The test should assert exact terminal disposition and preservation of the C refusal.

### GREEN 1 — minimum propagation

Implement only enough pure logic to satisfy the fixed fixture and canonical receipt identities.

### RED 2 — influence / authority separation

Add the same fixture with recognition ref R. R makes alternate candidate B2 eligible, but authority refs remain byte-for-byte identical.

### GREEN 2 — influence support

Add the minimum deterministic influence consultation seam.

### RED 3 — load without sovereignty

Run two declarations over identical topology/policy/authority with different budgets. The higher budget reveals an additional lawful candidate; authority/disclosure sets remain identical.

### GREEN 3 — budgeted frontier

Implement only the finite frontier behavior needed by the fixture.

### RED 4 — deterministic replay

Repeat canonical construction and propagation from identical declarations. Require identical declaration, step, refusal, and terminal addresses.

### GREEN 4 — replay proof

Reuse existing canonicalization/receipt infrastructure; do not introduce new hashing.

### Broad gate

```bash
npm run verify:all
```

must pass with no model, network, database, scheduler, or UI dependency.

## Required adversarial fixtures

1. sparse excitation produces multiple internal lawful steps;
2. authority union across steps is a subset of declaration authority;
3. influence changes eligibility without changing authority;
4. larger budget changes search reach without changing sovereignty;
5. an undeclared participant is refused;
6. missing disclosure basis refuses before inaccessible candidate details leak;
7. budget exhaustion is distinct from damping;
8. attempted refusal is distinguishable from never-considered candidate;
9. identical canonical inputs replay identically;
10. source seed/tension/recognition identities remain unchanged;
11. productive dissonance may terminate without synthetic resolution;
12. a branch cycle cannot run beyond declared finite limits.

## Compatibility and migration

The intended v0.1 effect is additive and experimental.

No migration is required for existing canonical node, relationship, NAV, World Encounter, Resonance Seed, or resonance-evaluator records.

If implementation requires:

- a tenth universal node kind;
- a new universal edge meaning;
- reinterpretation of `authorityRefs`;
- a second canonicalizer/hasher;
- new transport semantics that overlap World Encounter/BEE;
- autonomous scheduler/agent-loop semantics;

stop and produce an explicit ADR/version-boundary decision before implementation continues.

## Downstream adoption after proof

Only after the deterministic Project 0 specimen exists should downstream products explore creative runtime forms.

Potential adopters include:

- Haunted Toaster candidate-family mutation where discarded/recognized lineage alters future susceptibility without becoming a command;
- Haunted Phonograph motif development where rhythmic/harmonic evidence can excite later bounded transformations;
- Founder Node routing where field pressure can alter visible nearby moves without dispatch authority;
- Corpus OS branch exploration where refusal history changes navigational attention without rewriting case authority.

Those are downstream experiments, not acceptance requirements for Project 0 v0.1.

## Success criterion

The slice succeeds when an unfamiliar reviewer can inspect one branch declaration and its receipts and answer, without hidden runtime state:

1. What admitted the branch?
2. What could it see?
3. What authority could it use?
4. What influence could affect it without becoming authority?
5. Which local steps occurred and why?
6. Which attempted routes were refused?
7. Why did propagation stop?
8. Can the exact result be replayed offline?

If those answers require an ambient orchestrator, model transcript, or undocumented global state, the design has failed.
