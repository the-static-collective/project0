# Floor 1.1 Reference Kernel Design

**Issue:** #2 — Floor 1.1: implement the model-independent reference kernel  
**Branch:** `feat/floor-1.1-reference-kernel`  
**Status:** Approved design; implementation not yet started  
**Normative effect:** Additive executable reference implementation only; no ontology expansion and no change to existing canonical addresses.

## Purpose

Project 0 already has a settled canonical-addressing floor and an executable Witness residue subsystem, but it still lacks the small general-purpose kernel required by Floor 1.1. This slice makes the shared meaning contract mechanically usable without introducing a database, server, UI, model dependency, vector store, or second canonicalizer.

The kernel must make these existing laws executable together:

- stable identity through the existing RFC 8785/JCS canonical-addressing path;
- append-only receipt lineage;
- bounded, attributable, exhaustible authority;
- disclosure constraints independent from mere retrievability;
- pipeline admission independent from epistemic disposition;
- deterministic, offline conformance evidence with explicit unsupported remainder.

The design sentence is:

> A Project 0 act is admissible only when a declared object can be validated, canonically addressed, traced through append-only receipt history, and shown to fit the exact bounded authority and disclosure conditions of the requested act.

## Scope

### In scope

1. Canonical TypeScript domain types for nodes, relationships, disclosure policies, authority leases, receipts, and pipeline admission input/output.
2. Runtime validation with stable machine-readable reason codes.
3. Reuse of `src/canonical-addressing/index.ts` as the only canonical serialization and hashing path for Node, Edge, Receipt, and Request identities.
4. One append-only in-memory receipt graph with deterministic replay/query semantics.
5. Pure authority evaluation using immutable `LeaseGrant` receipts and append-only `LeaseConsumption` receipts.
6. Bounded consumption by invocation count, capability, recipient, scope, expiry, purpose, and disclosure policy.
7. Pipeline admission as a separate mechanical decision from epistemic disposition.
8. A deliberately small canonical/adversarial fixture subset derived from issues #3, #6, and #10.
9. Offline conformance reporting and a CLI-friendly output path.
10. Explicit `unsupported` results for fixture families that remain outside this slice.

### Out of scope

- database or durable storage adapters;
- network or API server;
- authentication provider;
- UI;
- model inference, embeddings, vector search, or automatic semantic scoring;
- TranchNode adapter implementation;
- a new receipt family unless an existing family is mechanically insufficient;
- a new canonicalizer, alternate hash format, or local serialization shortcut;
- changing the frozen nine Project 0 node kinds;
- merging the specialized Witness residue kernel into the generic receipt graph;
- completing every fixture in #3, #6, and #10.

## Architectural boundary

The kernel is additive and sits above the existing addressing floor.

```text
normative Project 0 contract
        ↓
runtime domain validation
        ↓
existing canonical-addressing module
        ↓
canonical Node / Edge / Receipt / Request identity
        ↓
append-only receipt graph
        ↓
authority + disclosure evaluation
        ↓
pipeline admission
        ↓
offline conformance report
```

`src/canonical-addressing/index.ts` remains the sole owner of RFC 8785/JCS canonicalization, domain separation, SHA-256 address construction, timestamp shape enforcement, structural guards, safe-integer guards, and traversal-depth bounds. Floor 1.1 imports it; Floor 1.1 does not fork, wrap with an alternative canonicalizer, or alter accepted canonical bytes.

The existing `src/witness-residue.ts` remains a specialized append-only Witness subsystem. Its expected-head concurrency guard, historical residue schema, replay logic, malformed-input residue, checker grants, and proof-attachment behavior are not generalized by implication. The Floor 1.1 receipt graph may reuse compatible patterns, but it owns only the generic receipt semantics required by issue #2.

The exact file split may be tightened during implementation, but responsibilities must remain isolated: validation must not mutate graph state; authority evaluation must be pure; graph append must not silently perform semantic judgment; conformance reporting must consume results rather than redefine them.

## Canonical domain types

### Node

The reference type preserves the frozen nine kinds and the required meaning-bearing fields already defined by Project 0. `id` is derived through the existing Node addressing path rather than accepted as arbitrary input when canonical identity is being minted.

Provenance is mechanically required where the normative node contract requires it. Validation distinguishes a structurally missing provenance declaration from provenance references that are present but cannot be resolved at a stateful admission boundary.

### Relationship

The reference relationship type preserves the required edge envelope and allowed finite edge types. Initial Floor 1.1 validation only implements the subset needed by the selected fixtures plus universal structural requirements. Unsupported edge-law checks report `UNSUPPORTED_CHECK` rather than being treated as passed.

### Disclosure policy

`DisclosurePolicy` is a typed portable contract used by evaluation. It is not a fifth semantic-address domain. Policies are referenced by already addressable Project 0 objects or stable declared policy references according to the existing contract.

Minimum evaluable fields:

- `policyRef`;
- permitted scope(s);
- permitted purpose(s);
- permitted recipient/actor constraints where applicable;
- revelation class or equivalent disclosure boundary.

The implementation must not infer a broader permission from absence of a restriction. Missing required policy evidence is an explicit refusal or indeterminate result.

### Authority lease

No mutable lease object becomes canonical state. The authority history is represented with existing receipt semantics:

- `LeaseGrant` defines the bounded delegation;
- `LeaseConsumption` records one successful use;
- optional later receipts may revoke or supersede effects without deleting either prior receipt.

A grant must expose enough information to evaluate:

- issuer;
- recipient;
- capability;
- scope;
- purpose where required;
- invocation limit;
- explicit validity bounds;
- issuing authority lineage;
- applicable disclosure policy refs.

Authority evaluation never calls `Date.now()` or another ambient clock. Every evaluation receives an explicit canonical timestamp, `evaluatedAt`, supplied by the caller/fixture. This keeps expiry checks replayable and offline-deterministic.

## Append-only receipt graph

The generic receipt graph is an in-memory reference structure optimized for deterministic conformance, not production storage.

### Required properties

1. Receipt identity is canonical and immutable.
2. Appending an identical canonical receipt is idempotent only when the canonical bytes are identical.
3. A different body cannot be installed at an existing receipt identity.
4. `previousReceiptRefs` must resolve before append unless a fixture explicitly tests unresolved input and expects refusal.
5. Appending never rewrites an earlier receipt.
6. Deterministic traversal order is defined and tested.
7. Query methods return copies/read-only values so callers cannot mutate stored canonical state.
8. Corruption or unresolved lineage returns stable failure codes instead of being silently skipped.

The graph is intentionally not a generic node/edge database. It is the smallest receipt-lineage mechanism needed to demonstrate the receipt and authority laws.

## Authority evaluation and bounded consumption

Authority evaluation is a pure function over a requested act, one `LeaseGrant`, applicable policy evidence, a receipt-history projection/cut, and explicit `evaluatedAt` time.

A request is permitted only when every applicable predicate passes. Required failures include at minimum:

- `AUTHORITY_MISSING`;
- `AUTHORITY_RECIPIENT_MISMATCH`;
- `AUTHORITY_CAPABILITY_MISMATCH`;
- `AUTHORITY_SCOPE_MISMATCH`;
- `AUTHORITY_PURPOSE_MISMATCH`;
- `AUTHORITY_EXPIRED`;
- `AUTHORITY_EXHAUSTED`;
- `DISCLOSURE_NOT_PERMITTED`;
- `AUTHORITY_LINEAGE_INVALID`;
- `PROVENANCE_REQUIRED`;
- `PROVENANCE_UNRESOLVED`.

Reason-code spellings are implementation constants and become compatibility surface once fixtures are committed. The design intent, not these draft spellings, is approved here.

### Consumption law

Consumption never decrements a field on the grant.

```text
LeaseGrant(invocationLimit = 2)
        ↓
LeaseConsumption #1
        ↓
LeaseConsumption #2
        ↓
next evaluation → AUTHORITY_EXHAUSTED
```

The remaining invocation count is derived from valid consumption receipts attributable to the grant at the selected receipt-graph cut. A failed or refused attempt does not consume authority unless a future normative rule explicitly says otherwise.

The successful act and its consumption receipt must be linked so replay can distinguish authorized capacity from recorded use.

## Pipeline admission vs epistemic disposition

These are independent outputs.

```ts
type PipelineAdmission =
  | { status: "admitted"; reasonCodes: [] }
  | { status: "refused"; reasonCodes: ReasonCode[] }
  | { status: "indeterminate"; reasonCodes: ReasonCode[] };

type EpistemicDisposition =
  | "supported"
  | "weak"
  | "disputed"
  | "rejected"
  | "unknown"
  | "not_evaluated";
```

The exact epistemic vocabulary should reuse existing Project 0 terms where normative text already fixes them; implementation must not introduce a synthetic truth score.

Examples the tests must preserve:

- epistemically useful material may still be pipeline-refused for disclosure or provenance;
- mechanically admissible material may remain disputed, weak, or unevaluated;
- authority success does not imply truth;
- epistemic confidence does not grant pipeline authority.

## Validation strategy

Validation is layered.

### Layer 1 — canonical-addressability

Call the existing canonical-addressing implementation. Unsupported runtime values, invalid timestamps, unsafe integers, cycles, sparse arrays, accessors, depth overflow, and related addressing failures surface unchanged or through stable mapped reason codes.

### Layer 2 — Project 0 structural contract

Validate required fields, frozen node-kind membership, receipt-family shape, policy references, authority-grant structure, required provenance declarations, and the selected relationship constraints required by the initial fixtures.

### Layer 3 — stateful admission predicates

Check receipt-parent existence, provenance-reference resolution where required, authority lineage, invocation exhaustion, disclosure bounds, and other predicates requiring graph state.

No layer is allowed to reinterpret a lower-layer failure as success.

## Initial fixture set

The first Floor 1.1 fixtures intentionally prove the machinery without claiming to finish all conformance work.

### Canonical fixtures

1. Repeated serialization of the same canonical object yields byte-identical canonical bytes and the same address.
2. Same apparent payload with materially different provenance yields different Node identity.
3. Same apparent payload with materially different disclosure yields different Node identity.
4. Append/get round trip returns the same immutable receipt identity.
5. Duplicate append of byte-identical receipt is idempotent.

### Authority/adversarial fixtures

6. Correct recipient + capability + scope + purpose + policy + valid `evaluatedAt` admits.
7. Wrong recipient refuses explicitly.
8. Wrong capability refuses explicitly.
9. Wrong scope refuses explicitly.
10. Grant expired at explicit `evaluatedAt` refuses explicitly.
11. Two-use grant admits twice and refuses the third use with exhaustion.
12. Missing/invalid authority lineage refuses explicitly.
13. Retrieval/existence of an object alone cannot satisfy authority evaluation.
14. Disclosure refusal leaves canonical history unchanged.
15. Missing required provenance refuses with `PROVENANCE_REQUIRED`.
16. Declared-but-unresolved required provenance refuses or becomes indeterminate with `PROVENANCE_UNRESOLVED`, according to the admission predicate being exercised.

### Receipt graph fixtures

17. Parent must exist before append.
18. Receipt identity cannot be replaced by different bytes/body.
19. Branching receipt history preserves both branches and common ancestry.
20. Deterministic traversal is stable across repeated runs.

### Admission orthogonality fixtures

21. Useful/disputed evidence can be pipeline-refused.
22. Pipeline-admitted material can remain epistemically `not_evaluated`.

### Unsupported remainder

Fixture families from #3/#6/#10 not implemented in this slice are emitted in the conformance report as `unsupported`, including at least repair scars, monument/build-beside, full sealed plurality, and any relationship-round-trip semantics not yet represented mechanically.

Unsupported is not pass and not fail. It means the current kernel does not claim coverage.

## Conformance report

The offline conformance surface returns structured data first and optionally renders a human-readable CLI view.

```ts
type ConformanceResult = {
  fixtureId: string;
  invariantIds: string[];
  status: "pass" | "fail" | "unsupported";
  reasonCodes: string[];
  evidenceRefs: string[];
};
```

Example rendering:

```text
PASS         P0-I4   stable-identity
PASS         P0-I7   bounded-authority
PASS         P0-I14  append-only-receipts
PASS         P0-I18  deterministic-verification
PASS         P0-I19  offline-survivability
UNSUPPORTED  P0-I5   repair-scar-round-trip
```

The process returns a nonzero exit code for actual conformance failures. Unsupported fixtures remain visible but do not masquerade as failures or successes. Whether unsupported coverage should make a future release gate fail is deferred to a later version-boundary decision rather than embedded accidentally in Floor 1.1.

## Error handling

Expected invalid input produces typed/stable reason codes or result objects. Programmer misuse may throw only at clear API boundaries where returning a meaningful conformance result is impossible.

No error path may:

- mutate a previously admitted receipt;
- consume authority after a refused act;
- silently broaden disclosure;
- erase rejected or unsupported evidence;
- convert malformed input into a valid canonical object by omission/defaulting;
- substitute ambient time for explicit `evaluatedAt`.

## Compatibility and migration

This slice is additive.

- Existing Node/Edge/Receipt/Request canonical addresses remain unchanged.
- The frozen nine-kind ontology remains unchanged.
- The existing Witness residue kernel remains valid and separate.
- No downstream application migration is required merely because Floor 1.1 exists.
- New reason-code constants and conformance fixture IDs become versioned compatibility surface after landing.
- A later persistent store must reproduce this kernel's observable append/replay semantics or declare a compatibility difference.

## Invariants exercised

Primary coverage:

- P0-I1 No silent rewrite;
- P0-I2 Provenance closure;
- P0-I4 Stable identity;
- P0-I6 Retrieval is not authority;
- P0-I7 Bounded authority;
- P0-I8 Disclosure travels with the object;
- P0-I9 Least revelation;
- P0-I11 Confidence is not evidence;
- P0-I13 Hashing is identity/tamper evidence;
- P0-I14 Receipts are append-only;
- P0-I18 Deterministic verification;
- P0-I19 Offline survivability;
- P0-I20 Explicit uncertainty.

The implementation plan must map each test to the invariant(s) it actually exercises rather than claiming blanket coverage.

## Stop conditions

Implementation must stop and return to design if any task requires:

1. changing canonical bytes or address grammar from the existing addressing module;
2. introducing a tenth universal node kind;
3. adding a new authority source not grounded in the existing receipt contract;
4. making successful verification, CI, witnessing, confidence, popularity, or retrieval itself grant authority;
5. mutating a `LeaseGrant` to record consumption;
6. letting epistemic disposition determine pipeline admission automatically;
7. collapsing the Witness residue kernel into the generic graph by implication;
8. hiding unsupported fixture coverage by reporting success;
9. adding infrastructure not required by the Floor 1.1 fixtures;
10. introducing nondeterministic ambient-time authority evaluation.

## Success criteria

Floor 1.1 is successful when:

- the reference kernel is runnable under the repository's existing TypeScript/Node toolchain;
- the existing canonical-addressing tests and Python cross-runtime verifier remain green;
- the new kernel tests are deterministic and offline;
- lease exhaustion is derived from append-only consumption history;
- invalid recipient, capability, scope, expiry, invocation count, provenance, authority lineage, and disclosure constraints fail explicitly;
- all time-sensitive authority tests use explicit `evaluatedAt` input;
- pipeline admission and epistemic disposition are demonstrably orthogonal;
- conformance output names fixture IDs, invariant IDs, status, reason codes, and evidence refs;
- unsupported fixture families are visible;
- no database, server, UI, model, vector store, second canonicalizer, or ontology expansion enters the slice.

## Follow-on doors intentionally left open

After this slice lands, the next work should become smaller rather than larger:

- #6 can add addressed-receipt and append-only graph vectors as conformance data;
- #3 can expand relationship-preserving round-trip cases;
- #10 can add sealed plurality, graft seams, repair scars, redaction overlays, and monument/build-beside fixtures;
- #7/#8/#9 can build versioned adapter/profile semantics against a real executable floor;
- TranchNode integration can consume explicit conformance behavior instead of interpreting prose alone.

That is the leverage target: Floor 1.1 should turn future semantic work into incremental fixtures and profiles rather than recurring kernel reinvention.
